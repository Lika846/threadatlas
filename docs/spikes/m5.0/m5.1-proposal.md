# M5.1 proposal: local embedding pipeline and storage (draft for review, 2026-11-10)

Status: **proposal only.** Nothing here is implemented or approved. It builds on
Experiments 1 and 2 (`experiment-1.md`, `experiment-2.md`) and the updated draft ADR 0002.

> **Update 2026-11-10:**
> - M5.1a was approved (D122) and implemented as described below.
> - For M5.1b, `docs/m5.1b-semantic-index-design.md` supersedes items 6–7. The
>   generation is (`contentHash`, `parserVersion`) plus a claim token, not
>   `contentHash` alone.

## Goal and boundary

**Goal:** ThreadAtlas can build and keep a local semantic index of imported conversations,
correctly through import, re-import, delete-all, cancellation and crashes, without
blocking the server and without any network access after an explicit model download.

**Not in M5.1:**
- the semantic or hybrid search UI (M5.2);
- related conversations (M5.3);
- rediscovery;
- larger models, `sqlite-vec` and topic grouping (M3).

Search stays keyword-only in M5.1. The index is built, verified and visible as a
status, but not yet queried by the UI.

## Split into two approvable slices

### M5.1a: embedder, chunker and model provisioning (no schema change)

1. **Dependencies** (production, needs approval): `onnxruntime-node@1.23.2` and
   `@huggingface/tokenizers@0.2.0`, both pinned exactly.
2. **Model provisioning:** `npm run model:fetch`, an explicit command run by the user
   and the only network step.
   - It downloads the four pinned files of `Xenova/multilingual-e5-small` at
     `761b726d…`.
   - It saves them to `data/models/multilingual-e5-small/` (git-ignored, beside the
     database).
   - Before moving a file into place, it checks the size and SHA-256 listed in a
     checked-in manifest.
   - The app never downloads anything itself. Without the model it works as today,
     keyword search only, and Settings explains how to enable semantic indexing.
3. **Embedder** (`src/lib/semantic/embedder.ts`): the direct pipeline from Experiment 2.
   - Prefixes, reference truncation (keep `</s>`), mean pooling, normalisation.
   - Batches are made per conversation, sorted by length.
   - It runs only in a worker thread (`src/lib/semantic/worker.ts`) that owns the
     session.
   - Cancellation is cooperative, between batches. Shutdown drains: stop claiming, await
     the in-flight batch, release the session, terminate the worker.
   - Errors are returned as codes; no text or vectors are ever logged.
4. **Chunker** (`src/lib/semantic/chunker.ts`): sentence-packed chunks of up to 64
   tokens, with one sentence of overlap and exact character offsets. Only visible,
   non-structural messages on the displayed path are chunked, the same rule as keyword
   search.
5. **Tests:**
   - unit tests for the chunker (offsets are exact substrings, overlap, over-long
     sentences, empty and whitespace messages), quantisation and truncation;
   - an opt-in real-model test, which runs only when the model files are present,
     comparing against a checked-in synthetic fixture of expected vectors (cosine
     ≥ 0.9999);
   - the network tripwire and `lsof` sampling;
   - a responsiveness test (event-loop p99 with the worker running).

### M5.1b: storage, lifecycle and status (one additive migration)

6. **Migration (additive only, existing tables untouched)**, reviewed and rehearsed like
   M2.1:

   | Table | Columns | Notes |
   | --- | --- | --- |
   | `EmbeddingChunk` | `conversationId`, `contentHash` (the conversation version embedded), `sourceNodeId`, `chunkIndex`, `start`, `end`, `vector` | `conversationId` references the conversation with cascade delete; `vector` is int8 plus a scale (388 bytes), or float32 (1,536 bytes) — decision 3; unique on (`conversationId`, `sourceNodeId`, `chunkIndex`) |
   | `EmbeddingJob` | `conversationId` (primary key), `contentHash`, `state` (`pending` / `running`), `attempts`, `updatedAt` | references the conversation with cascade delete |
   | `EmbeddingIndex` | `modelId`, `modelRevision`, `chunkerVersion`, `dims`, `quantisation`, `epoch` | a single row |

   `Conversation.contentHash`, which already changes whenever an import replaces a
   conversation, is the generation. The strict drift check is extended to the three new
   tables.
7. **Lifecycle** (invariants I1–I6 from Experiment 2, with the content hash as the
   generation):
   - **Import:** a replacing import deletes the conversation's chunks and upserts a job,
     inside the existing replacement transaction (`persist/conversation.ts`). A new
     conversation gets a job; an unchanged one keeps its chunks.
   - **Delete-all:** clears both tables (also through the cascade) and bumps the epoch.
     Its existing secure delete, VACUUM and verification are extended to the new tables.
   - **The indexer:**
     - claims a job in a short transaction and runs inference outside any lock;
     - commits under the existing write lock, compare-and-set on `contentHash` and the
       epoch;
     - resets running jobs at start-up.
   - **Model or chunker change:** if `EmbeddingIndex` doesn't match the current
     configuration, all chunks are dropped and every conversation is queued.
8. **Trigger and status** (Settings, "Semantic index"):
   - **Status:** model present or missing, indexed / remaining conversations, chunks, last
     error code.
   - **Buttons:** Start indexing, Pause. Both are guarded Server Actions with the same
     Origin, Host and `Next-Action` checks as delete-all.
   - **Indexing doesn't start automatically** after an import (decision 5). Progress is
     polled while the page is open.
9. **Shutdown:** a SIGINT/SIGTERM handler drains the worker. Where to register it under
   `next start` and `next dev` is the first thing M5.1b checks (`instrumentation.ts` or
   the module that owns the singleton). If it can't drain, the abort on exit is
   documented as harmless to data.
10. **Tests:**
    - integration tests for every lifecycle case, using a deterministic fake embedder for
      speed:
      - re-import and delete-all during inference;
      - cancellation and resume;
      - a SIGKILL child followed by recovery;
      - configuration change;
      - stale-chunk guard;
      - no duplicates;
      - `integrity_check`;
    - delete-all residue check with a canary vector (chunks store offsets, not text);
    - drift check;
    - e2e for the Settings status and Start/Pause flow with the fake embedder (no model in
      CI). The real-model e2e is opt-in.

## Risks

- **Runtime support:** ONNX Runtime 1.23.2 is the last Intel Mac build. The
  production dependency is pinned, so upgrading means leaving this Mac or switching
  runtimes (ADR 0002 records the exit options).
- **Size:** about 247 MB of `node_modules`, mostly other platforms' binaries.
- **Shutdown:** an abort on exit during inference remains possible if the server is killed
  mid-batch; no data is lost.
- **Indexing time:** about 40 minutes for 50,000 messages on this Mac, so the progress
  display and resumability matter.
- **Index size:** for 50,000 messages, about 105,000 chunks. That is about 41 MB on disk
  as int8, 160 MB as float32, and 37–154 MB for the cache.

## Estimate

M5.1a: one session. M5.1b: two sessions (migration rehearsal, lifecycle, Settings). Each
slice stops for review before commit.

## Decisions needed

1. **Runtime:** direct ONNX Runtime 1.23.2 with `@huggingface/tokenizers` as production
   dependencies (recommended), knowing it pins the Intel Mac build.
2. **Chunking:** 64-token sentence chunks with reference truncation (recommended).
3. **Vector format:** int8 (recommended: no measured quality loss, a quarter of the
   space), or float32.
4. **Model provisioning:** an explicit `npm run model:fetch` with a checked-in manifest of
   hashes, files in `data/models/` (recommended).
5. **Indexing trigger:** manual Start from Settings (recommended for M5.1), or automatic
   after each import.
6. **Hybrid rule for M5.2:** the gated rule, fusing keyword results only when the
   exact-word query matches (recommended), decided now so it isn't tuned later.
7. **Independent relevance judgements:** would you write or review about 10 queries
   before M5.2?
8. **Commit the research material:** Experiments 1 and 2, the long evaluation set and
   the ADR draft, as research documents. Nothing in them is application code.
9. **A larger model:** test one later only for cross-language buried ideas (deepx 0.37).
   Recommended: not before M5.2.
