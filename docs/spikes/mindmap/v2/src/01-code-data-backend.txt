=== t001 | Merge two CSV files on customer id | py-data | - | en
U: I have orders.csv and customers.csv. When I merge them on customer_id I end up with fewer rows than orders.csv has. Why are rows disappearing?
A: A plain `merge` is an inner join by default, so any order whose customer_id has no match in customers.csv is dropped. Use `how="left"` to keep every order:

```python
merged = orders.merge(customers, on="customer_id", how="left", indicator=True)
print(merged["_merge"].value_counts())
```

The `indicator` column tells you which rows found no customer. Also check the dtypes: if one file reads the id as int and the other as string, nothing will match even when the values look identical.
U: the dtype thing was it, one was object. thanks
A: Classic one. `customers["customer_id"] = customers["customer_id"].astype(int)` before the merge, or pass `dtype={"customer_id": str}` to both `read_csv` calls so they agree from the start.

=== t005 | Jupyter kernel keeps dying | py-data | - | en
U: My notebook kernel dies every time I load a 6 GB CSV. Laptop has 16 GB RAM.
A: Loading with default dtypes often needs 2–3× the file size in memory, so 6 GB on disk can easily exceed what's free. Options, from easiest:

1. Read only the columns you need: `usecols=[...]`.
2. Give compact dtypes: `dtype={"store": "category", "qty": "int32"}`.
3. Process in chunks: `for part in pd.read_csv(path, chunksize=500_000): ...` and aggregate as you go.
4. Convert once to Parquet; later loads are faster and smaller.

If you only need aggregates, chunking plus a running groupby usually solves it without changing tools.

A: Nice. Saving it as Parquet now will make every later load take seconds instead of minutes.

A: The row sums have shape (100,), which numpy lines up with the last axis (3), not the first. Keep the summed axis with `keepdims`:


Now the sums are (100, 1) and broadcast across the three columns as you intended.

=== t008 | Rens telefonnumre i et regneark med Python | py-data | - | no
U: Jeg har en kolonne med telefonnumre skrevet på alle mulige måter: "+47 912 34 567", "91234567", "0047-912-34-567". Hvordan får jeg dem like?
A: Fjern alt som ikke er sifre, og kutt landskoden:

```python
import re

def rens(nr):
    siffer = re.sub(r"\D", "", str(nr))
    if siffer.startswith("0047"):
        siffer = siffer[4:]
    elif siffer.startswith("47") and len(siffer) == 10:
        siffer = siffer[2:]
    return siffer if len(siffer) == 8 else None

df["telefon"] = df["telefon"].map(rens)
```

Rader som blir `None` har ikke et gyldig norsk nummer og bør sjekkes for hånd.

=== t014 | Missing values: fill or drop? | py-data | - | en
U: About 8% of the income column is missing in my survey data. Should I drop those rows or fill them with the mean?
A: It depends on why they're missing. If people with high incomes skip the question more often, dropping or mean-filling both bias your results downwards. A few practical steps:

- Compare the respondents with and without income on age, education and region. Big differences mean the data isn't missing at random.
- For a quick analysis, fill with the median within groups (e.g. by education level), and add a flag column `income_missing` so the model can learn from the gap itself.
- For anything you'll publish, consider multiple imputation and report results both ways.

8% is not much, so if the groups look similar, dropping is defensible and simplest to explain.

=== t019 | JWT token expires too fast | web-backend | - | en
U: Users get logged out every 15 minutes. Should I just make the JWT valid for a week?
A: A week-long access token is risky: if one leaks, it can't be revoked. The usual pattern is two tokens:
- a short access token (5–15 minutes) sent with every request;
- a long refresh token (days or weeks) stored in an httpOnly cookie, used only to get a new access token.
When an API call returns 401, the client calls `/refresh` quietly and retries. Users stay logged in, and you can revoke refresh tokens in the database when someone logs out or changes their password.

=== t020 | Postgres connection pool exhausted | web-backend | sql | en
U: Under load our Node service starts failing with "sorry, too many clients already". Pool max is 20, we run 8 instances.
A: 8 instances × 20 connections = 160, and Postgres defaults to `max_connections = 100`. Each instance is allowed to open more than the server will accept. Options:
1. Lower the pool size per instance (e.g. 10), which is usually enough because queries are short.
2. Put PgBouncer in transaction mode in front of Postgres so many client connections share a few server connections.
3. Check for leaks: a route that does `pool.connect()` without `release()` on an error path will slowly eat the pool.
Start with 3 — leaks look exactly like load problems and no setting fixes them.

=== t024 | Rate limiting a public endpoint | web-backend | - | en

A: For a single instance, `express-rate-limit` is enough:

```js
const rateLimit = require("express-rate-limit");
app.post("/signup", rateLimit({ windowMs: 15 * 60 * 1000, max: 5 }), signupHandler);
```

With several instances behind a load balancer, store the counters in Redis (`rate-limit-redis`) so the limit is shared. Make sure `app.set("trust proxy", 1)` is on behind a proxy, otherwise every request looks like it comes from the load balancer's IP and you'll block everyone at once.

=== t025 | Webhook from Stripe fails signature check | web-backend | - | en

A: Stripe signs the raw request body. If a JSON body parser runs first, the body you verify is re-serialised and no longer matches. Use the raw body for that route only:

```js
app.post("/webhook", express.raw({ type: "application/json" }), (req, res) => {
  const event = stripe.webhooks.constructEvent(req.body, req.headers["stripe-signature"], secret);
  ...
});
```

and register `express.json()` after it (or exclude this path). Also double-check you use the signing secret for this endpoint, not your API key; the CLI and the dashboard give different secrets.

=== t026 | Background jobs in a web app | web-backend | - | en
U: After a user uploads a video we need to make thumbnails, which takes a minute. Right now the request just hangs. What's the normal way to do this?
A: Move the work out of the request:
1. The upload handler saves the file, creates a job row (status "pending") and returns immediately with the job id.
2. A worker process picks up jobs from a queue (Celery or RQ with Redis in Python, BullMQ in Node), makes the thumbnails and sets the status to "done".
3. The page polls `/jobs/<id>` every few seconds, or you push an update over a websocket.
For low volume, a database table polled by one worker is perfectly fine and avoids adding Redis.
U: and if the worker crashes halfway?
A: Make the job safe to run twice: write thumbnails to a temporary name and rename at the end, and mark the job "running" with a timestamp. A job that has been "running" for much longer than usual gets reset to "pending" and retried. Cap retries at three and keep the last error message on the row so you can see what went wrong.

=== t029 | Websocket disconnects every 60 seconds | web-backend | - | en
U: my websocket connection drops exactly every 60 seconds in production but not locally
A: Exactly 60 seconds points to an idle timeout in something between the browser and your server — Nginx's `proxy_read_timeout` defaults to 60s, and many load balancers do the same. Two fixes, ideally both:
- send a ping from the server every 25–30 seconds so the connection is never idle;
- raise the proxy timeout for the websocket location (`proxy_read_timeout 3600s;`) and make sure the `Upgrade` and `Connection` headers are passed through.
