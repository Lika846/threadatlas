=== t042 | Хук для загрузки данных с повтором | frontend | web-backend | ru
U: Напиши хук useFetch, который повторяет запрос до 3 раз при ошибке сети.
A: Вот простой вариант:

```ts
function useFetch<T>(url: string) {
  const [state, setState] = useState<{ data?: T; error?: string; loading: boolean }>({ loading: true });
  useEffect(() => {
    let cancelled = false;
    (async () => {
      for (let attempt = 1; attempt <= 3; attempt++) {
        try {
          const r = await fetch(url);
          if (!r.ok) throw new Error(String(r.status));
          const data = await r.json();
          if (!cancelled) setState({ data, loading: false });
          return;
        } catch (e) {
          if (attempt === 3 && !cancelled) setState({ error: String(e), loading: false });
          await new Promise(res => setTimeout(res, 500 * attempt));
        }
      }
    })();
    return () => { cancelled = true; };
  }, [url]);
  return state;
}
```

Повторять имеет смысл только сетевые ошибки и 5xx; на 4xx повтор ничего не даст. Для серьёзного проекта лучше взять TanStack Query — там повторы, кэш и отмена уже есть.

=== t055 | Window function: running total per customer | sql | - | en
U: I need a running total of payments per customer ordered by date in Postgres.
A: Use `SUM` as a window function partitioned by customer:

```sql
SELECT customer_id, paid_at, amount,
       SUM(amount) OVER (PARTITION BY customer_id ORDER BY paid_at
                         ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW) AS running_total
FROM payments
ORDER BY customer_id, paid_at;
```

The explicit `ROWS` frame matters when two payments share a timestamp; the default `RANGE` frame would give them the same running total.

=== t063 | Deadlock between two transactions | sql | web-backend | en
U: We get "deadlock detected" a few times a day when two requests transfer money between the same accounts in opposite directions.
A: Each transaction locks the first account, then waits for the second, which the other transaction already holds. Fix it by always locking accounts in the same order, for example by id:

```sql
SELECT * FROM accounts WHERE id IN ($1, $2) ORDER BY id FOR UPDATE;
```

Then do both updates. Also retry the whole transaction once on a deadlock error; occasional deadlocks are normal in busy systems and a retry is the standard handling.
