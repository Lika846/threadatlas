# M5.1b-2 plan: inference host, server integration and Settings

Status: **approved 2026-11-12 and implemented (slices 1–4, notes at the end); committed.**

Builds on: `docs/m5.1b-semantic-index-design.md` (§5.7, §8, §11, §12 and the M5.1b-1
notes), the shutdown comparison (`docs/spikes/m5.1b/shutdown/README.md`), the integration
spike (`docs/spikes/m5.1b/integration/README.md`), ADR 0002, and the committed M5.1b-1 core
(`524efc3`). No research is repeated; where evidence is missing, this plan says so and
puts it in the tests.

## 0. Summary

- **Inference runs in one child process**, started only by an explicit Start and ended
  at the end of every run. It is the M5.1a worker loop (`serveWorker`, unchanged) behind a
  small IPC adapter, hardened from the spike's prototype. The Next.js server never loads
  ONNX Runtime.
- **One server-side service** on `globalThis` owns the session: Start, Pause, Retry
  failed, status. It calls the existing `runIndexer` with a child-process embedder. No
  new tables, no schema change.
- **Next.js keeps its default signal handling.** No `NEXT_MANUAL_SIG_HANDLE`, no
  `NEXT_EXIT_TIMEOUT_MS`, no `instrumentation.ts`. When the server exits, however it
  exits, the child drains and exits by itself; the claimed row is shown as *interrupted*
  and reset at the next Start.
- **Settings gets a "Semantic index" section:** Start, Pause, Retry failed, counts,
  static state messages, polling every 2 s.
- **Two small changes to M5.1b-1 code**, each a decision below: refund the attempt when
  Start resets an interrupted row (§4.6), and take the indexer lock before starting the
  child (§4.3).

## 2. Architecture and component boundaries

```
 Browser (Settings)                         Next.js server process (no ONNX Runtime)
 ┌───────────────────────────┐  Server     ┌──────────────────────────────────────────────┐
 │ SemanticIndexPanel        │  Actions    │ settings/semantic-actions.ts (guarded)        │
 │  Start · Pause · Retry    ├────────────►│   └─► index/service.ts  (globalThis singleton)│
 │  counts · state message   │  poll 2 s   │         ├─ runIndexer(writer, reader, …)      │
 └───────────────────────────┘◄────────────┤         │    ├─ write lock / indexer lock     │
                                           │         │    └─ SQLite (getWriterDb, getDb)   │
                                           │         └─ InferenceProcess (client)          │
                                           └───────────────────┬──────────────────────────┘
                                                               │ IPC (fork, advanced serialisation)
                                           ┌───────────────────▼──────────────────────────┐
                                           │ Child: inference-child.ts                    │
                                           │  child-core.ts (IPC adapter, drain, watchdog) │
                                           │   └─ serveWorker (unchanged) → pipeline/ONNX │
                                           │  no database, no network, no logging          │
                                           └──────────────────────────────────────────────┘
```

**Boundaries:**
- **The child** knows the model and nothing else: no database, no paths except the model
  directory, no network, no logging. It receives only message texts it must chunk or
  embed.
- **The client** (`InferenceProcess`) implements the existing `IndexEmbedder` interface,
  so the indexer does not change. It turns every child failure into an `EmbeddingError`
  code.
- **The service** is the only module the app calls. It owns the single session per server
  process and composes status. It is the only importer of `inference-process.ts`.
- **The database layer** keeps all cross-process guarantees (write lock, indexer lock,
  I2–I6). The service adds none of its own.

## 3. The inference host

### 3.1 Start-up and model initialisation

1. The service checks the model directory with `verifyModelDir(dir, manifest, { hash:
   false })` (sizes and presence, a few `stat` calls). `MODEL_MISSING`, `MODEL_INVALID` or
   `MODEL_DIR_INVALID` end the Start before anything is spawned.
2. `fork(/* turbopackIgnore: true */ entry, [], { serialization: "advanced", execArgv: [],
   env: {}, stdio: ["ignore", "ignore", "ignore", "ipc"] })`:
   - `entry` is `<cwd>/src/lib/semantic/inference-child.ts`, loaded from source by Node's
     type stripping, as approved for the worker in D124. It must exist, otherwise
     `RUNTIME_UNAVAILABLE`;
   - the same Node binary as the server (`fork` default), an empty environment (no proxy
     variables, no `DATABASE_URL`), no inherited flags, and stdio discarded, so native
     messages never reach the server's logs.
3. The parent sends `init { modelDir, verifyHashes: true }` as the first IPC message (not
   argv, so nothing appears in `ps`). The child verifies sizes and SHA-256, loads the
   pipeline and replies `ready { info }` or `init-error { code }`, then exits.
4. **Start-up timeout:** 60 s from fork to `ready` (measured 1.1–1.3 s). On expiry, SIGKILL
   the child and fail with `MODEL_LOAD_FAILED`. Killing is safe here: it ends only the
   child, and an operating-system kill does not abort native code.
5. The indexer then checks the reported versions and dimensions against the code
   (`INDEX_CONFIG_MISMATCH`), as today.

### 3.2 IPC protocol

The existing `WorkerRequest` and `WorkerResponse` are reused. The only differences:
`embed` has no shared-memory cancel flag, because memory cannot be shared across
processes; cancellation is a message; and initialisation is a message.

| Direction | Message | Notes |
| --- | --- | --- |
| parent → child | `init { modelDir, verifyHashes }` | first and only once; anything before it is ignored |
| parent → child | `chunk { id, messages }` | one page (≤ 200 messages, ≤ 1,000,000 characters) |
| parent → child | `embed { id, kind: "passage", texts }` | one window (≤ 256 chunk texts) |
| parent → child | `cancel { id }` | the child sets that request's flag; stops before the next batch |
| parent → child | `shutdown` | queued after the in-flight request; release, `closed`, exit |
| child → parent | `ready { info }` / `init-error { code }` | exactly one of them, first |
| child → parent | `chunked { id, chunks }` / `embedded { id, data: Float32Array }` | `data.length` must equal `texts.length × dimensions` |
| child → parent | `error { id, code }` | codes only |
| child → parent | `closed` | the session has been released; nothing can be inferring |

**Rules:**
- **One request in flight.** The client refuses a second concurrent call (`INVALID_INPUT`,
  a programming error); the indexer is sequential.
- **Ids increase.** A reply with an unknown id is ignored. A reply of the wrong type, or
  with a wrong data length, rejects with `WORKER_FAILED`.
- **Validation happens on both sides:** the existing `LIMITS` in the client, and
  `serveWorker`'s `validate` in the child. The indexer's own checks stay as they are:
  exact substrings, vector lengths, `validChunkRows`.
- **Nothing but codes crosses as an error.** Texts cross only in requests and in
  `chunked` replies. They are never logged on either side.

### 3.3 Bounds on requests and memory

- **Request size:** a `chunk` request carries at most one page: ≤ 1,000,000 characters,
  at most about 4 MB as UTF-16. Its reply carries the chunk texts with their overlap, at
  most about 2× that. An `embed` request is ≤ 256 texts; its reply is 256 × 384 × 4 bytes
  ≈ 393 KB.
- **Server memory during a run:** the int8 results of one conversation (≤ 20,000 × 388
  bytes ≈ 7.8 MB, cap D124) plus one page and its chunks. The server stays ≈ 80 MB when
  idle; all model memory lives in the child and is returned when it exits (measured).
- **Child memory:** 0.73–0.87 GB while indexing (measured). There is at most **one child
  per server process** (the service) and **one indexing child per database** (the
  indexer lock, taken before the fork, §4.3).
- **No idle child:** the child exits at the end of every run, so ThreadAtlas holds no
  model memory between runs. Query-time embedding in M5.2 will decide its own lifetime.

### 3.4 Ownership and single instance

- The child belongs to the service's session object on `globalThis`. Nothing else forks
  it, and the session holds the only reference to it.
- It is spawned in the server's process group (not `detached`), so a terminal Ctrl-C
  reaches it too; it drains on SIGINT as it does on disconnect (measured).
- **Single instance across processes:** the indexer lock (`<db>.index-lock`). A second
  ThreadAtlas process gets `INDEXER_BUSY` before it forks (§4.3), and its status shows
  *indexing in another ThreadAtlas process*.

### 3.5 Crashes and restart policy

- **A crash in the child** (native abort, OOM kill, unexpected exit): the IPC channel
  closes, the pending call rejects `WORKER_FAILED`, and the run stops with the attempt
  **kept**, as §5.6 already specifies. Keyword search and the rest of the app keep
  running (measured in the spike: the server stayed up and answered 200).
- **No automatic restart within a run.** The user starts again. A conversation that
  crashes the child 3 times becomes `failed` (`WORKER_FAILED`) instead of stopping every
  run. Retry failed gives it another chance. This needs no new state and cannot loop
  without a user action.
- **Request watchdog:** if a request gets no reply within 120 s (a window takes about
  0.3–0.6 s, a page chunking well under 10 s), the client SIGKILLs the child and rejects
  `WORKER_FAILED`. With a child process this is safe: the kill ends only the child, and
  an operating-system kill does not abort native code. It turns a hung native call into
  an ordinary crash. *(Decision 3.)*

### 3.6 Cooperative cancellation and shutdown

```
 child:  spawned ─init─► loading ─ready─► idle ⇄ busy (one request)
                           │                 │
                    init-error/exit     shutdown msg · IPC disconnect · SIGINT/SIGTERM
                           │                 │      · IPC error · uncaughtException
                           ▼                 ▼
                         exited ◄─exit 0── released ◄─(in-flight batch finishes)─ draining
```

- **Pause (user):** the service aborts the run's signal. The indexer sends `cancel` for
  the in-flight request; the child stops before its next batch (≤ one batch, measured
  0.34–0.41 s). The indexer refunds the claimed row (unchanged M5.1b-1 code), then
  `close()`: `shutdown` → `closed` → natural exit. Never killed while inferring.
- **Every path to the drain in the child is the same:** a `shutdown` message, IPC
  `disconnect` (the parent exited, however), SIGINT/SIGTERM, an IPC `error`, or an
  uncaught exception. Each sets every cancel flag and queues `shutdown`. Sends use an
  error callback, so a closing channel can never raise an unhandled `error` event. This
  is the defect the spike found and fixed.
- **After release:** the child exits by itself. A 1 s timer forces `process.exit(0)`
  only after release, when nothing native is running.
- **Parent-side `close()`:** waits for `closed` or exit. It SIGKILLs only if the child has
  not exited 5 s after reporting `closed`, as in M5.1a.

### 3.7 Next.js development reloads and production shutdown

- **HMR edit:** the service state lives on `globalThis`, so an edit re-evaluates the
  module but reuses the session and its child. There is no second child (spike: a
  module-scoped handle leaked one per edit). A run in progress keeps the code it started
  with. The next Start forks a fresh child from the current source, and a changed
  version is caught by `INDEX_CONFIG_MISMATCH`.
- **`next.config.ts` change or a full dev restart:** the old server process exits; its
  child drains on `disconnect` and exits 0 (spike: 60 ms). The new server has no session.
  The claimed row is *interrupted* until the next Start. The D124 dev-only limitation
  disappears.
- **`next start` SIGTERM/SIGINT, or SIGKILL:** Next exits with its defaults. The child
  drains on `disconnect` (spike: 44–72 ms SIGTERM, 59–60 ms SIGKILL, no orphan in 31
  runs). The OS releases both locks; a T2 in progress rolls back (rollback journal). The
  row is *interrupted*, then reset at the next Start.

### 3.8 Orphan prevention

1. **Primary:** IPC `disconnect` → drain → exit (measured in every parent-death case).
2. **Backstop 1:** the child checks `process.ppid` every 1 s (an unref'd timer). If it
   changes (re-parented to launchd), the child drains as on `disconnect`.
3. **Backstop 2:** if the parent is gone and the session is still not released 30 s
   later (a hang inside native code), the child exits anyway. That may abort the child,
   but nothing depends on it any more, it holds no data, and it never touches the
   database. *(Decision 4.)*
4. **Server side:** the service never forks while a session exists, and `close()` is
   awaited before the session is cleared.

### 3.9 Offline operation and privacy

- **No network code** in the child or the client. ONNX Runtime and the tokenizer are
  local packages, and `model:fetch` is never called by the app.
- **Empty child environment and discarded stdio:** no inherited proxy or telemetry
  variables, and no native output in the server's logs.
- **No logging** anywhere in the host, client or service. Results and status carry static
  codes and counts only, never texts, ids, paths or native messages.
- **Verified** by connection sampling during the integration and e2e tests, and by a test
  that pins the `fork` options (§7).

### 3.10 Against the worker-thread approach

The evidence is already in `docs/spikes/m5.1b/shutdown/README.md`; nothing new is needed
to choose.

| | Worker thread | Child process (proposed) |
| --- | --- | --- |
| Shutdown during a batch | needs `NEXT_MANUAL_SIG_HANDLE` (production-only documented) and `NEXT_EXIT_TIMEOUT_MS` (undocumented); without them the server aborts | works with Next's defaults; the child drains on its own |
| Native crash | ends the web server | ends only the child; the app keeps running |
| Memory after a run | ≈ 0.75 GB stays in the server | all returned (server ≈ 80 MB) |
| Dev config change mid-batch | kills `next dev` | normal restart |
| Cost | — | +0.25 s start, −3% throughput, +40–170 MB while indexing |
| New failure modes | — | IPC errors must never end the child (tested); a native hang could outlive the server (backstops in §3.8) |

## 4. Next.js integration

### 4.1 The service (`src/lib/semantic/index/service.ts`, server-only)

State on `globalThis.__threadatlasSemantic`:
`{ session: { abort, live: LiveIndexerState, done: Promise<void> } | null, lastRun: { outcome, code } | null }`.

```
            start() ──model check fails──► idle  (lastRun = not-started, code)
              │
   idle ──────┴──► starting ──fork/ready──► running ⇄ waiting-for-import
    ▲                 │                       │  ╲
    │       not-started (INDEXER_BUSY,        │   pause() ──► pausing ──► idle (paused)
    │       MODEL_*, RUNTIME_*, MISMATCH)     │
    │                 ▼                       ├──► finished ──► idle (lastRun = finished)
    └──────────── idle ◄──────────────────────┴──► stopped(code) ──► idle (code also stored in DB)
```

- **`start()`** is synchronous up to the point where the session is created: `if
  (state.session) return "already-running"`, then it creates the session and only then
  awaits anything. In one Node process two Starts cannot both pass, so the in-process
  check needs no lock. The run is not awaited by the action. It continues in the server
  process (`next start` is a long-lived Node server), and its promise always settles
  into `lastRun`, never rejecting unhandled.
- **`pause()`** aborts the session's controller and returns at once. The status shows
  *pausing* until the run settles. Calling it with no session does nothing.
- **`retryFailed()`** runs `store.retryFailed` in a writer transaction under the write lock
  (`IMPORT_LOCK_WAIT_MS`). A busy lock gives a static "busy, try again" result. It is
  allowed while a run is active: the loop picks the rows up.
- **`status()`** combines `computeIndexStatus(getDb(), { live, probe })`, the model check
  (sizes only, no hashing on every poll) and `lastRun`. It never writes.

### 4.2 Start, Pause and Retry

These are Server Actions in `src/app/settings/semantic-actions.ts`. Each calls
`checkServerActionRequest` first, takes no input, returns a fixed-shape state with a
static message, and never logs, all as in the delete-all actions. Start is idempotent
while running. Nothing starts indexing on startup, after an import, or after Retry.

### 4.3 Concurrent sessions: take the indexer lock before forking *(Decision 2)*

Today `runIndexer` opens the embedder first and then takes the indexer lock. With a
child that means spawning an 800 MB process only to receive `INDEXER_BUSY`. Proposed:
take the lock first, then open the embedder, then check versions. Nothing is written in
either order, and the lock order (indexer lock, then write lock) is unchanged. The
existing tests for `INDEXER_BUSY` and `INDEX_CONFIG_MISMATCH` cover the change.

### 4.4 Imports and delete-all

No new coordination; it is already in the database layer (M5.1b-1, tested):
- **An import replacing a conversation** invalidates it (I2) and clears the token. The
  in-flight claim stops at its next page or is refused at T2.
- **Delete-all** removes chunks and status rows and moves the epoch (I3). The run finds
  no rows and finishes. Delete-all is **not** blocked or paused by indexing, and indexing
  never blocks an import: it waits for the write lock and shows *waiting for import*.

### 4.5 Progress and error reporting

- **Counts:** from the database (indexed, waiting, running, failed, too large, chunks, of
  all conversations), so they are right across restarts and processes.
- **Live state:** from the session (`running`, `waiting-for-import`, `pausing`), or from
  the indexer-lock probe (*indexing elsewhere*).
- **Run-level failures:** stored by the indexer (`setRunError`) and shown after a restart.
  Not-started codes are kept in `lastRun` in memory: the action returns them immediately,
  and polling shows them until the next Start.
- No rate or time estimate in this milestone (counts only).

### 4.6 Application restarts: refund interrupted attempts *(Decision 1)*

Today, Reconcile's reset of dead `running` rows (I5) keeps the attempt, because with a
worker thread a native crash caused by an input killed the server. With the child
process, an input that crashes inference crashes only the child, and the live server
records it as `WORKER_FAILED` with the attempt kept (§3.5). A row left `running` can then
only mean the server process itself stopped: a shutdown, a dev restart, SIGKILL.

Proposed: the I5 reset refunds the attempt (`attempts = MAX(attempts − 1, 0)`). Otherwise
three ordinary restarts during one long conversation would mark it `failed`. **Cost:** a
conversation that crashes the *server* (not the child) would be retried at every manual
Start. That is never automatic, and keyword search is unaffected. The change is one SQL
line in `store.ts`, plus its test.

### 4.7 No duplicate processes on reload

`globalThis` state, as above. The child handle is never module-scoped. The service
module imports `node:child_process` only through the client. A test simulates a module
re-evaluation (a fresh import of the module with the same `globalThis`) and requires the
same session and child pid.

## 5. Settings UI

A section **"Semantic index"** above *Delete all imported data*, using the existing
classes (`BUTTON`, `TONE`, the `role="status"` / `aria-live="polite"` pattern of
`DataPanel`).

```
 Semantic index
 Builds a local search index of your conversations with a model on this computer.
 Nothing leaves your machine. Keyword search works with or without it.

 ┌ status (TONE by state) ─────────────────────────────────────────────┐
 │ Indexing… 1,204 of 3,310 conversations indexed.                      │
 └──────────────────────────────────────────────────────────────────────┘
   Indexed 1,204 · Waiting 2,083 · In progress 1 · Failed 22 (3 too large)
   [ Start indexing ]  [ Pause ]  [ Retry failed ]
```

- **Buttons:**
  - **Start indexing** (*Resume* when something is waiting) is disabled while running,
    while indexing elsewhere, and when the model is missing or invalid;
  - **Pause** is shown only while running; it reads *Pausing…* until the batch ends;
  - **Retry failed** is shown when there are failures.
- **Polling:** every 2 s while the page is visible (stopped while the tab is hidden),
  through a no-input Server Action returning `{ state, counts, model, lastRun }`:
  counts and codes only, no text, ids or paths. Server Actions keep the existing guard
  and need no new route. Next.js queues actions, so a click can wait behind one poll of a
  few milliseconds. *(Decision 5: alternatively a GET route with its own guard.)*
- **States and static messages** (one table in `index/messages.ts`, unit-tested):

| State | Message (abridged) | Tone |
| --- | --- | --- |
| model missing | "The semantic model is not installed. Run `npm run model:fetch`, then reload." | warning |
| model invalid | "The model files don't match the approved version. Run `npm run model:fetch` to replace them." | error |
| never indexed / waiting | "N conversations are not indexed yet." | neutral |
| indexing / waiting for import | "Indexing… X of Y" / "Waiting for an import to finish…" | neutral |
| pausing / paused | "Pausing after the current batch…" / "Paused. N waiting." | neutral |
| interrupted | "Indexing was interrupted (ThreadAtlas stopped). N conversations will be indexed at the next Start." | warning |
| indexing elsewhere | "Another ThreadAtlas window or process is indexing this database." | neutral |
| incompatible | "The index was built with a different model or settings and will be rebuilt at the next Start." | warning |
| run failed / not started | the code's static message (`EMBEDDING_ERRORS` or an index code) | error |
| finished with failures | "Indexed X. N failed (M too large to index); keyword search still finds them." | warning |
| up to date | "All N conversations are indexed." | success |

## 7. Test plan

All synthetic. The fake child runs the real IPC adapter and the real `serveWorker` loop
with the fake pipeline. Unit and integration tests run in plain Node; e2e uses a built
server, as today.

| --- | --- | --- |
| Child start-up and shutdown | ready, versions reported; `close()` → `closed` → exit 0; pid gone afterwards; init-error codes for missing/invalid model; start-up timeout → kill, `MODEL_LOAD_FAILED` | int |
| Fork options (privacy) | `env` empty, stdio ignored, `execArgv` empty, init not in argv | unit |
| Crash during inference without crashing the server | fake child `process.abort()` mid-batch → `WORKER_FAILED`, parent alive, run stopped, attempt kept; e2e: the server answers `/` and keyword search afterwards | int + e2e |

| Restart and recovery | Start after a crash forks a new child and completes; 3 crashes on one conversation → `failed`, the others indexed; the parent SIGKILLed mid-batch (child-process harness) → the child exits 0, no orphan; the next Start resets the row with the attempt refunded (decision 1) | int |
| IPC errors never end the child mid-batch | the parent killed at random points during a batch (20 iterations) → child exit code 0, no orphan, no abort | int |
| Pause during a batch | slow batches; pause mid-batch → the batch completes (event log), row `pending`, attempts unchanged, child exited 0, lock released | int |

## 8. Risks and trade-offs

- **Source loading at runtime:** the child entry is read from `src/` under the working
  directory, as approved for the worker in D124. `npm run start` must run from the
  project root (already true for Prisma). A wrong directory gives
  `RUNTIME_UNAVAILABLE`, not a crash.
- **Node type stripping for the child entry:** Node 24 runs it by default. A future Node
  change would surface as `RUNTIME_UNAVAILABLE` and in the model tests.
- **Background run after an action returns:** fine for the long-lived `next start` and
  `next dev` servers ThreadAtlas uses. It would not suit serverless hosting, which is out
  of scope.
- **Interrupted rows and refunds (decision 1):** trades a theoretical retry loop of a
  server-crashing input, never automatic, against failing healthy conversations after
  restarts.
- **Watchdog kills (decisions 3 and 4):** a kill ends only the child. The watchdog's
  timeout must stay far above real batch times; slow machines are covered by the 120 s
  margin (≥ 200 × the measured window time).
- **Extra memory while indexing:** +40–170 MB for the second runtime, ≈ 0.9 GB in total,
  only during a manual run.
- **Polling through Server Actions:** a click can queue behind one in-flight poll; polls
  are a few milliseconds.
- **Dev-only code staleness:** a run in progress during an HMR edit keeps its old code
  until it ends. This is harmless: versions are checked at every Start.

## 9. Decisions requested

1. **Approve the child-process host** (§3) as the production architecture, with Next.js
   default signal handling. The `NEXT_MANUAL_SIG_HANDLE` / `NEXT_EXIT_TIMEOUT_MS`
   workaround (D124, testing-only) is dropped.
2. **Refund the attempt when Start resets an interrupted row** (§4.6). A one-line change
   to M5.1b-1's I5.
3. **Take the indexer lock before forking** (§4.3). A reorder in `runIndexer`.
4. **Watchdogs:** a 120 s request timeout and a 60 s start-up timeout in the client
   (SIGKILL of the child only); a ppid check and a 30 s orphan backstop in the child
   (§3.5, §3.8).
5. **Polling transport:** a no-input Server Action (recommended) or a GET route with a
   custom-header guard.
6. **Test seam:** `THREADATLAS_INFERENCE_ENTRY`, honoured only under a test runner and
   only for files in `tests/helpers/`, so the e2e server can use the fake child.
7. **Keep the worker-thread `Embedder` for tests only,** with an import-boundary test,
   rather than deleting it now. The model tests and the indexer, status and crash test files use it.
   Retiring it later is a separate clean-up.

   - The thread arms only when the parent is confirmed gone (`process.ppid` changed, that
     is, the child was re-parented). IPC `disconnect` alone only starts the drain.

     itself. It never signals another process.

   that is releasing normally is never killed.

## Slice 2 implementation notes (2026-11-12, for review)

Owner's approval: Slice 1 accepted; Slice 2 only (indexer integration and interrupted
attempts). Implemented, uncommitted. No schema, dependency, service, Server Action or UI
change.

### 1. Lock order

`runIndexer` now takes the indexer lock first, then opens the embedder (the inference
child), then checks versions. The lock order is unchanged: indexer lock, then write lock.
A competing process gets `INDEXER_BUSY` before any child starts or any model loads.
Embedder `close()` (the drain) still runs before the lock is released. The lock and the
exit listener are released on every path: init error, start-up timeout, configuration
mismatch, an unexpected error, a child crash, a request timeout, a pause and a finished
run, each tested.

### 2. Interrupted attempts: the policy (owner's condition 2)

**Decision 2 of the plan is not implemented as written.** It refunded the attempt when
Start resets an interrupted row. The crash-window review showed that this cannot tell an
ordinary restart from a conversation that makes the *server* die, and the latter would be
retried without limit.

**What is implemented instead** needs no new persistent state and no schema change:
- **The I5 reset is unchanged:** it keeps the attempt.
- **A normal exit refunds synchronously.** While a claim's inference is in progress, a
  normal process exit (`process.exit`: Next.js's default SIGTERM/SIGINT handling, dev
  restarts) refunds the attempt in an `exit` listener (`index/exit-refund.ts`). The refund
  is one non-blocking try of the write lock, then one guarded UPDATE on a fresh SQLite
  connection with no busy wait. Anything not immediately possible is skipped, which keeps
  the attempt.
- **A hard death keeps the attempt.** SIGKILL, a crash or an OOM kill runs no code.
- **Failures always count.** Once a child crash, a request timeout or an inference failure
  is observed for the claim, the exit listener no longer offers it for a refund. Such an
  attempt therefore counts even if the server exits before recording it.

### Crash windows

| Window | Normal exit | Hard death |
| --- | --- | --- |
| Inside T1 (claim) | rolled back, nothing consumed | rolled back |
| Inference in progress | **refunded** at exit | kept, reset at the next Start |
| Child crash or request timeout observed, not yet recorded | kept (not offered for a refund) | kept |
| Child crash recorded (`worker-crash`) | kept (pending, `failed` after 3) | kept |
| Inference failure (`INFERENCE_FAILED`) observed, not yet recorded | kept | kept |
| Inside T2 (this process holds the write lock) | refund skipped: kept (≤ about 0.2 s per conversation) | kept, T2 rolled back |
| An import in this process holds the write lock | refund skipped: kept | kept |
| After T2 | committed | committed |
| Pause, stale discard, run-level stop (recorded) | refunded, as before | refunded, as before |

**Results:**
- A conversation that keeps crashing the child (or the server, by a hard death) is
  claimed once per Start and becomes `failed` after three Starts. Each Start ends after one
  crash (one inference process per Start, never restarted within a run).
- Retry failed resets it to three new attempts, and `lastErrorCode` is kept.
- `INFERENCE_FAILED` keeps its in-run retries.

**Limitations:**
- **The refund depends on `process.exit`.** Next.js's default handling calls it (from
  the shutdown spike); a host that dies by a bare signal keeps the attempt. To be verified
  with a real Next.js server in slice 3 or 4.
- **One narrow race:** the child dies, and the server exits normally before it has
  observed the death (milliseconds). The claim is then refunded and that one crash is not
  counted. It needs a user stop at that moment every time, so it cannot loop by itself.

### 3. Test hygiene

- **The fake child's crash is now SIGKILL of itself by default**, which leaves no macOS

- **Real native aborts (`process.abort()`, SIGABRT) are opt-in** with

  not yet recorded.
- **`IndexerDeps.registerExitHandler`** (test-only): captures the exit listener.

  - `CHILD_HOST=process` runs the child indexer with the inference child process;

  - **a fix for a latent flake in the M5.1b-1 harness.** A lock "held forever" was
    reachable only from a suspended async function, so garbage collection could close its

### Tests

  indexers in one process; a child indexer with the process host.
