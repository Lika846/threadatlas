# M5.1b-1 implementation plan: persistent index core

Status: **for approval, 2026-11-11.** It implements the approved parts of
`docs/m5.1b-semantic-index-design.md` (D123, D124) with the reviewed migration in
`docs/spikes/m5.1b/migration/` (SHA-256 `e761409d…598d`). Nothing below is implemented
yet.

## Scope

**In M5.1b-1:**
- the migration;
- status invalidation in import (I2) and delete-all (I3);
- the indexer lock and its probe;
- the indexer loop: Start/Reconcile, claim, pages, windows, commit, failure classes,
  pause;
- the vector reader with its compatibility checks;
- read-only status computation;
- tests;
- docs.

The indexer is driven from tests and the opt-in model test only.

**Not in M5.1b-1** (M5.1b-2, separate approval):
- any Next.js wiring: no route, Server Action or Settings UI;
- the inference host for the server (child process, if approved; see
  `docs/spikes/m5.1b/shutdown/`);
- signal handling and polling.

Also out of scope: search (M5.2), and the real-database migration (a separate approval,
see the end of this plan).

## Steps

### 1. Schema and migration

- **Files:** `prisma/schema.prisma` becomes byte-identical to
  `docs/spikes/m5.1b/migration/schema.prisma`, and
  `prisma/migrations/20261111120000_semantic_index/migration.sql` byte-identical to the
  reviewed `migration.sql`. Then `npm run db:generate`.
- **Tests:**
  - `tests/semantic-migration.test.ts`: the file's SHA-256 equals the reviewed one; it is
    `BEGIN`, 3 `CREATE TABLE "Embedding…"`, 2 `CREATE INDEX`, `COMMIT`, and nothing
    else, in the same style as `tests/search-migration.test.ts`.
  - `src/lib/db/schema.int.test.ts`: the new tables, columns, primary keys, indexes and
    both cascading foreign keys; no `sqlite_sequence`.
  - `npm run db:check-migrations` passes unchanged (only the FTS5 difference).
  - The rehearsal harness is committed as an **opt-in** integration test
    (`THREADATLAS_REHEARSAL=1`; about 20 s, it runs the Prisma CLI).

### 2. Constants

- `src/lib/semantic/index/config.ts`:
  - `INDEX_ROW_ID = "main"`;
  - `MAX_ATTEMPTS = 3`;
  - `PAGE_MAX_MESSAGES = 200`, `PAGE_MAX_CODE_UNITS = 1_000_000`;
  - `WINDOW_CHUNKS = 256`;
  - **`MAX_CHUNKS_PER_CONVERSATION = 20_000`** (internal constant, not configurable);
  - the states `pending | running | indexed | failed`;
  - new static error codes `CONVERSATION_TOO_LARGE`, `INDEX_CONFIG_MISMATCH`,
    `INDEXER_BUSY`, `INDEX_EMPTY`, `INDEX_INCOMPATIBLE`.
- `EMBEDDING_VERSION` (`model-manifest.ts`) gains `-window256`. Nothing is stored yet,
  so this changes no data.

### 3. The SQL store

- **File:** `src/lib/semantic/index/store.ts`.
- **Contents:** the prototype's statements, unchanged in substance:
  - `invalidateConversation(tx, id)` (I2);
  - `reconcile(tx, config)`;
  - `claimNext(tx)` (T1, `UPDATE … RETURNING`);
  - `readPage(db, claim, after)`, which re-checks version and token in the same query;
  - `commitClaim(tx, claim, chunks, workerConfig)` (T2, one compare-and-set, inserts of at
    most 500 rows);
  - `failClaim(db, claim, class, code)`, `retryFailed(db)`, `counts(db)`.
- **Conventions:** positional `?` raw SQL through `runWriterTransaction`, and a
  `DateTime` helper tested against the adapter's stored format.

### 4. Import integration (I2)

- **Change:** `src/lib/import/persist/conversation.ts` calls `invalidateConversation(tx,
  id)` once, in the add and replace branches, after the messages are written and before
  the batch counters. Nothing else in the import changes.
- **Tests:**
  - the decision table for cases 5–13, ported from the prototype;
  - rollback at every `TxStage` leaves the status row and chunks unchanged;
  - a replacement during inference (cases 7 and 8) makes the commit stale;
  - the existing import performance and responsiveness tests stay within their limits
    (the cost is one indexed delete and one upsert per written conversation).

### 5. Delete-all integration (I3)

- **Phase 1** (the existing transaction):
  - explicit `DELETE` of all chunk and status rows (the cascade stays as a second line);
  - increment `epoch` and `changeCounter` if the `EmbeddingIndex` row exists;
  - the row is kept.
- **Phase 2:** verification adds "both tables empty". `finishStorageCleanup` refuses
  while any chunk or status row exists.
- **Tests:**
  - canary vectors absent from the file afterwards;
  - the epoch increases and never resets;
  - a commit in flight is refused;
  - the existing delete-all, crash and e2e tests stay green.

### 6. The indexer lock

- **Implementation:** `write-lock.ts` is generalised to take the lock-file suffix (same
  mechanism, `<db>.index-lock`), with `probeIndexerLock(dbPath)`: try once, release at
  once.
- **Tests:**
  - cross-process exclusion;
  - release on SIGKILL;
  - a repeated race test: probes never make a concurrent Start fail (Start retries,
    about 150 ms).

### 7. The indexer

- **File:** `src/lib/semantic/index/indexer.ts`: `runIndexer({ writer, dbPath, openEmbedder,
  signal, hooks })`.
- **Embedder interface:** `IndexEmbedder` (`info`, `chunk`, `embedPassages`, `close`).
  M5.1b-1 uses the existing `Embedder` (Node-loaded worker; tests and the opt-in model
  test) and a fake. M5.1b-2 plugs in the server host.
- **Start:**
  1. open the embedder (model check), and compare the versions it reports with the
     code's (`INDEX_CONFIG_MISMATCH`);
  2. take the indexer lock (`INDEXER_BUSY`);
  3. Reconcile.
- **Loop:**
  - claim;
  - read pages;
  - `chunk` per page;
  - embed windows of at most 256 chunks;
  - quantise each window to int8 at once;
  - count against the cap: over 20,000 chunks, or a message over the worker's input
    limit, fails the conversation **permanently** with `CONVERSATION_TOO_LARGE`. That
    affects no other row and does not touch keyword search;
  - commit.
- **Failure classes** (§5.6, approved):
  - recoverable: retried, then `failed` after 3 attempts;
  - permanent: `failed` at once;
  - run-level: the run stops and the attempt is refunded;
  - worker crash: the attempt is kept.
- **Waiting and pausing:**
  - a busy write lock: wait 1 s, not an attempt;
  - pause (an `AbortSignal`): cancel, the batch finishes, the row goes back to `pending`
    (attempt refunded), then close the embedder and release the lock.

### 8. The reader

- **File:** `src/lib/semantic/index/reader.ts`: `openVectorReader(db, queryInfo)`.
- **Behaviour:**
  - `INDEX_EMPTY` / `INDEX_INCOMPATIBLE` from the five configuration fields and the
    query worker's versions;
  - the I6 join;
  - the byte-length check, with skipped rows counted;
  - one read transaction.
- **Use:** nothing in the app calls it yet.

### 9. Status (read-only)

- **File:** `src/lib/semantic/index/status.ts`: `computeIndexStatus(db, { live, probe })`.
- **Output:** counts (indexed, waiting, failed and too large, chunks) and one state from
  §11 of the design, including *interrupted* (stale `running` rows, lock free) and
  *indexing in another process* (correction D). It never writes.

### 10. Tests named in the review (D) and the design (§12)

All of them run with the deterministic fake embedder through a real worker thread,
unless noted.

- **Zero-chunk completion:** only hidden, structural or whitespace messages give
  `indexed` with `chunkCount 0`; three further Starts queue nothing.
- **Oversized conversations:**
  - a synthetic conversation at the cap commits in one transaction (heap growth and T2
    duration recorded; target < 500 ms);
  - cap + 1, and a message over the input limit, fail permanently with one attempt;
  - the others are indexed;
  - keyword search finds the oversized one.
- **Failed jobs:**
  - poison (recoverable): `failed` after 3, the others indexed;
  - a run-level failure refunds the attempt;
  - a worker crash keeps it;
  - "retry failed" resets.
- **A→B→A:** I2 driven twice during one inference; the commit is refused by the token,
  then re-embedded.
- **Model-version incompatibility:**
  - each configuration field changed in turn: the reader returns `INDEX_INCOMPATIBLE`
    before Reconcile;
  - a query worker on another version is refused;
  - Reconcile drops the chunks, increments the epoch and requeues;
  - a worker on the old version cannot commit.
- **Invalidation (C):** cases 5–13 through the real import, and replacement during
  inference for cases 7 and 8.
- **Lifecycle:**
  - backfill;
  - pages and windows: a replacement between pages stops at once with no attempt
    counted;
  - window determinism: bit-identical vectors on reindex and in a fresh process;
  - pause during a batch;
  - cancel and resume;
  - write-lock contention;
  - a second process refused;
  - stale against live `running` rows (correction D);
  - event-loop responsiveness.
- **Crash recovery:** SIGKILL of a child indexer process at each crash point (inside
  T1, during inference, inside T2, after T2). Afterwards: no duplicates, the chunk set
  equals a full rebuild, `integrity_check` ok.
- **Opt-in real model** (`npm run test:model`): index the two research sets through the
  indexer; chunk count and nDCG equal the M5.1a model tests (re-measured with the window
  rule).

## After approval of the implementation: the real database

- **Ordering:** once I2 is in the import code, the app needs the new tables, so the
  commit and the real-database migration go together (as for M2.1). Each needs its own
  approval at that time.
- **Procedure** (design §10):
  1. stop the server;
  2. check that no process holds the database or its lock;
  3. make a fresh backup with the backup API into `data/backups/`, with a manifest,
     verified;
  4. run `npm run db:deploy`;
  5. verify as in the rehearsal.
- **Not touched:** the existing M2.1 backup.

## Risks

- **Import cost:** one delete and one upsert per written conversation. Measured by the
  existing import performance tests; expected to be small next to rewriting every
  message.
- **The `'main'` row id is a convention,** not a constraint (Prisma cannot express a
  CHECK). The store is the only writer.
- **Raw SQL against Prisma-managed tables:** the adapter's `DateTime` format and the
  positional parameters are pinned by tests. A Prisma upgrade re-runs them.
- **The 20,000-chunk cap is an estimate** (about 1.3 million tokens per conversation).
  Measured at the cap in the tests; a larger real conversation fails visibly, never
  silently.
