## 1. Scope

**In M5.1b:**
- one additive migration with three new tables;
- the indexing lifecycle: queueing, claiming, committing, invalidation, recovery;
- the vector-read function with its compatibility checks (used by M5.2, tested here);
- delete-all integration;
- the server integration: worker loading, the process-wide singleton, signal handling;
- a status panel in Settings with Start and Pause;
- tests.

**Not in M5.1b:**
- semantic or hybrid search and the in-memory vector cache (M5.2);
- related conversations;
- automatic indexing after an import;
- larger models;
- `output: "standalone"`.

## 2. Correction to the M5.1 proposal: the generation (approved, decision 1)

The proposal used `Conversation.contentHash` alone as the generation. **That is not
enough.**

- A re-import of identical source with a newer parser keeps the same `contentHash` but
  replaces every message (`decide.ts`, case 7, `CONVERSATION_REPROCESSED`).
- A conversation's message set is fully determined by the pair (`contentHash`,
  `parserVersion`). This design uses that pair, plus:
  - a per-claim random token, which every import touching the conversation clears;
  - an index epoch.

Either the token or the pair alone would prevent a stale commit; both are checked.

## 3. Tables (one additive migration)

The migration creates the three tables and their indexes and nothing else. No existing
table, column, index, trigger or row changes.

### `EmbeddingIndex`: one row, the index configuration and state

| Column | Type | Notes |
| --- | --- | --- |
| `id` | TEXT PK | always `'main'` (reviewed migration; an integer key would make Prisma emit `AUTOINCREMENT` and SQLite's `sqlite_sequence`) |
| `epoch` | INTEGER NOT NULL | incremented by delete-all and by every configuration change; never decreases (the row survives delete-all, decision 4) |
| `embeddingVersion` | TEXT NOT NULL | `EMBEDDING_VERSION`: model, revision, model file, prefixes, truncation, pooling, batching and windowing (§5.4) |
| `chunkerVersion` | TEXT NOT NULL | `CHUNKER_VERSION` (`sentence-pack-v1`) |
| `chunkTokens` | INTEGER NOT NULL | 64 |
| `quantization` | TEXT NOT NULL | `QUANTIZATION_VERSION` (`int8-absmax-v1`) |
| `dimensions` | INTEGER NOT NULL | 384 |
| `changeCounter` | INTEGER NOT NULL | incremented by every commit or deletion of chunks (cache invalidation in M5.2) |
| `lastErrorCode` | TEXT NULL | last run-level error code (static codes only) |
| `updatedAt` | DATETIME NOT NULL | |

The row is created on first Start, not by the migration. A missing row means "never
indexed".

### `EmbeddingStatus`: one row per conversation, its indexing state (renamed, correction A)

The previous revision called this `EmbeddingJob` and deleted the row on success. It is now
kept after success with state `indexed` and its chunk count. That is what stops a
conversation with zero eligible messages being queued again forever (§5.2).

| Column | Type | Notes |
| --- | --- | --- |
| `conversationId` | TEXT PK | FK → `Conversation(id)` ON DELETE CASCADE |
| `contentHash` | TEXT NOT NULL | conversation version this row refers to |
| `parserVersion` | TEXT NOT NULL | conversation version this row refers to |
| `epoch` | INTEGER NOT NULL | index epoch when queued; for `indexed`, the epoch of the commit |
| `state` | TEXT NOT NULL | `pending` / `running` / `indexed` / `failed` (validated in TypeScript, like other enums) |
| `claimToken` | TEXT NULL | random 128-bit hex while `running`; cleared by any re-queue |
| `attempts` | INTEGER NOT NULL | see §5.6; `failed` after 3 |
| `chunkCount` | INTEGER NULL | set when `indexed` (0 is valid) |
| `lastErrorCode` | TEXT NULL | e.g. `INFERENCE_FAILED`, `CONVERSATION_TOO_LARGE` |
| `queuedAt`, `updatedAt` | DATETIME NOT NULL | |

Index: (`state`, `queuedAt`), for claiming in queue order and for the status counts.

### `EmbeddingChunk`: one row per chunk vector (unchanged)

| Column | Type | Notes |
| --- | --- | --- |
| `conversationId` | TEXT NOT NULL | FK → `Conversation(id)` ON DELETE CASCADE; part of the primary key |
| `contentHash`, `parserVersion` | TEXT NOT NULL | the conversation version embedded |
| `epoch` | INTEGER NOT NULL | index epoch at commit |
| `sourceNodeId` | TEXT NOT NULL | message provenance (A62); joined to `Message` for display |
| `chunkIndex` | INTEGER NOT NULL | position within the message |
| `start`, `end` | INTEGER NOT NULL | UTF-16 offsets into `Message.contentText` |
| `tokenCount` | INTEGER NOT NULL | ≤ 64 |
| `chunkKey` | TEXT NOT NULL | the chunker's content-addressed id (32 hex) |
| `vector` | BLOB NOT NULL | `int8-absmax-v1`, 388 bytes |

Keys and indexes (reviewed migration):
- **primary key** (`conversationId`, `sourceNodeId`, `chunkIndex`). The draft of §3 had
  a separate rowid `id` and a unique index; the composite key avoids `AUTOINCREMENT`
  (whose `sqlite_sequence` counter would survive delete-all and a rollback) and saves
  one index;
- (`epoch`).

**No text is stored.** Chunk text is always `Message.contentText.slice(start, end)`, read
when needed. This keeps imported text in one place for delete-all and secure deletion.

**Size:** about 2 chunks per visible message, so about 105,000 rows and roughly
45–50 MB including the index for 50,000 messages. `EmbeddingStatus` adds one small row per
conversation.

### Prisma

- The three tables are ordinary Prisma models (`Bytes` for the vector), so the client
  can read them and the drift check covers them without special cases.
- **Migration file hygiene:** a Prisma-generated migration also proposes to drop the 10
  FTS5 tables. Those statements are removed by hand, as for every migration since M2.1.
  The reviewed SQL contains only `CREATE TABLE` and `CREATE INDEX`. Never `migrate dev`.
- **Bulk writes:** chunk inserts use positional `?` raw statements inside the
  interactive transaction (the adapter rejects `?1`), at most 500 rows per statement.

## 4. Invariants

| # | Invariant | Enforced by |
| --- | --- | --- |
| I1 | A conversation's version is (`contentHash`, `parserVersion`); its id is stable across replacement, and a re-import after delete-all gets a new id | existing import code |
| I2 | Every write that replaces or adds a conversation deletes its chunks and resets its status row (state `pending`, token cleared, attempts 0, chunk count cleared, new version, current epoch) **in the same transaction** | `persist/conversation.ts` |
| I3 | Delete-all deletes every chunk, status row and conversation in one transaction and increments the epoch | `delete-all.ts` |
| I4 | A commit writes a conversation's chunks and sets its status `indexed` in one transaction, only if all four hold: the row still has this claim's token; row, conversation and claim agree on version; the epoch is unchanged; the stored configuration equals the configuration reported by the running worker. Otherwise nothing is written | indexer commit |
| I5 | Only the process holding the indexer lock (§6) runs jobs. At lock acquisition every `running` row belongs to a dead run and is reset to `pending`. **A `running` row is shown as live only if its run is (correction D, §5.8)** | indexer start; status |
| I6 | Every read of vectors joins `EmbeddingChunk` to `Conversation` on id **and** version, and requires `chunk.epoch = EmbeddingIndex.epoch`. A stale row that escaped I2–I4 could still never be returned | the vector-read function (§7) |
| I7 | **(correction B)** The vector-read function returns nothing unless the stored configuration (all five fields) equals the code's and the querying worker's. A configuration change is unreadable before Reconcile runs | the vector-read function (§7) |
| I8 | **(correction C)** The indexer's memory for one conversation is bounded: one page of message text and one window of float vectors at a time, plus int8 results up to a fixed chunk cap. The commit stays one transaction | the indexer loop (§5.4) |

## 5. Lifecycle

### 5.1 Import and re-import (inside the existing per-conversation transaction)

- **add:** insert a status row (`pending`, current epoch, or 0 when no `EmbeddingIndex`
  row exists).
- **replace** (cases including `CONVERSATION_REPROCESSED`):
  - delete the conversation's chunks;
  - upsert its status row to `pending` with the new version, `claimToken = NULL`,
    `attempts = 0`, `chunkCount = NULL`;
  - increment `changeCounter` if any chunk was deleted.
- **unchanged / older / flagged / skipped:** nothing.

Cost: one indexed delete and one upsert per written conversation, inside a transaction
that already rewrites every message.

### 5.2 Start (manual, from Settings)

1. Check the model directory (`verifyModelDir`, sizes and SHA-256) and start the worker.
   - On failure, show `MODEL_MISSING`, `MODEL_INVALID`, `RUNTIME_UNAVAILABLE` or
     `MODEL_LOAD_FAILED` with its static message. Nothing is written.
   - The worker's reported `embeddingVersion` and `chunkerVersion` must equal the code's
     constants; otherwise `INDEX_CONFIG_MISMATCH`. Under `next dev` this catches a worker
     running older code than the server after an edit.
2. Take the indexer lock (§6); otherwise report `INDEXER_BUSY` (another ThreadAtlas
   process is indexing).
3. **Reconcile**, under the write lock, in one short transaction:
   - create the `EmbeddingIndex` row if missing;
   - if any configuration field differs from the code's:
     - delete all chunks;
     - set every status row to `pending` (token cleared, attempts 0, chunk count
       cleared, current version);
     - increment the epoch and store the new configuration;
   - reset `running` rows to `pending` (I5);
   - **(correction A)** insert a `pending` row only for conversations that have **no
     status row**. An `indexed` row with `chunkCount = 0` (no eligible messages) and a
     `failed` row are never queued again by Reconcile. This is the backfill for
     conversations imported before M5.1b.
   - **Defensive:** a row whose version differs from its conversation's (which I2 makes
     impossible) is reset to `pending` and counted.
4. Run the loop.

### 5.3 The loop (one conversation at a time)

- **T1, claim** (write lock, short transaction):
  - pick the oldest `pending` row;
  - set `running` and a fresh `claimToken`, and increment `attempts` (§5.6);
  - read the conversation's version, the epoch, and the **ids and text lengths** of its
    visible messages, in path order: `pathIndex` not null, not structural, not hidden;
    the same rule as keyword search. No message text is read here.
  - release the lock.
- **Inference** (no lock, no transaction): pages and windows (§5.4).
- **T2, commit** (write lock, one transaction):
  - check I4;
  - delete any chunks of the conversation (defensive), insert the new ones;
  - set the status row `indexed`, with `chunkCount`, the claim's version and epoch, and
    the token cleared;
  - increment `changeCounter`.

  If I4 fails, write nothing and count a *stale discard*. A newer row (from a re-import)
  is already `pending`. After delete-all there is no row.
- **Zero eligible messages:** T2 commits zero chunks and `indexed` with `chunkCount = 0`.

### 5.4 Bounded memory for long conversations (correction C)

The previous revision read all messages in T1 and embedded the whole conversation in one
call. A very long conversation (the import accepts files up to 50 MiB) would then hold
all its text, chunks and float vectors in memory at once.

- **Pages:** message text is read in pages at message boundaries, up to 200 messages or
  1,000,000 UTF-16 code units each.
  - Each page is a short read with no lock.
  - The same query checks that the conversation's version still equals the claim's and
    that the status row still holds this claim's token. If not, stop at once: a stale
    discard, with no attempt counted.
- **Windows:** the page's chunks (from `Embedder.chunk`) are embedded in calls of at most
  256 chunks, in chunk order.
  - The window rule is deterministic (it depends only on the conversation's content), so
    incremental indexing still equals a full rebuild.
  - Because batch composition affects the int8 model's outputs, the rule becomes part of
    `EMBEDDING_VERSION` (`…/batch16-sorted-window256`).
  - Nothing is stored yet, so this changes no data.
- **Results:** after each window the main thread quantises to int8 (388 bytes) and drops
  the float vectors (1,536 bytes each). It keeps only the int8 vector and the chunk's
  offsets, about 0.45 KB per chunk.
- **Cap:** at most 20,000 chunks per conversation, about 9 MB held until T2. That is
  about 1.3 million tokens, or roughly 5 MB of text.
  - A larger conversation, or a single message over the worker's 1,000,000-character
    input limit, fails at once with `CONVERSATION_TOO_LARGE`. That is permanent, with no
    retries (§5.6), and Settings shows it.
  - Nothing partial is indexed.
- **Consistency:**
  - The pages may come from different snapshots only if the conversation changed during
    the run. Any such change resets the status row (I2), so the token check at the next
    page, or I4 in T2, discards the work.
  - T2 remains one transaction (all chunks or none).
- **Peak memory:** one page of text (≤ 2 MB), one window of tensors, the int8 results,
  and the worker's measured ≈ 0.7 GB. Measured in M5.1b with a synthetic conversation at
  the cap, which also measures how long T2 holds the write lock (target < 500 ms).

### 5.5 Write-lock contention

- An import holds the write lock for its whole run. The indexer never waits on it inside
  a transaction.
- A busy lock pauses the loop, retried every 1 s, and the status shows "waiting for
  import". Waiting never counts as an attempt.

### 5.6 Failures and attempts (decision 3, with its condition)

`attempts` is incremented at claim (T1), so a conversation that crashes the process
still counts. A run-level failure detected cleanly gives the attempt back.

| Class | Codes | Effect |
| --- | --- | --- |
| Recoverable, per conversation | `INFERENCE_FAILED` | back to `pending` with `lastErrorCode`, or `failed` after 3 attempts; the run continues with the next row |
| Permanent, per conversation | `CONVERSATION_TOO_LARGE`, `INVALID_INPUT` | `failed` at once; the run continues |
| Run-level: model, runtime, configuration, database | `MODEL_MISSING`, `MODEL_INVALID`, `RUNTIME_UNAVAILABLE`, `MODEL_LOAD_FAILED`, `INDEX_CONFIG_MISMATCH`, `CLOSED`, database errors | **the run stops**; the claimed row goes back to `pending` and its attempt is refunded; `EmbeddingIndex.lastErrorCode` is set |
| Worker died during this conversation | `WORKER_FAILED` | the run stops; the attempt **is kept**, so a conversation that kills the worker 3 times becomes `failed` instead of stopping every run |
| Not a failure | pause, cancel, stale discard, write lock busy | the row goes back to `pending` (or is already replaced); no attempt counted |

"Retry failed" in Settings resets `failed` rows to `pending` with `attempts = 0`.

### 5.7 Pause, cancellation and shutdown (decision 5, with its condition; spike results)

> **2026-11-11 (D124):** the `NEXT_MANUAL_SIG_HANDLE` / `NEXT_EXIT_TIMEOUT_MS` approach
> below is approved **for testing only**, not as the final architecture. The bounded
> comparison (`docs/spikes/m5.1b/shutdown/`) recommends a **child process** for native
> inference instead. With it, Next.js keeps its default signal handling. The child
> drains by itself when the server exits, however the server exits, and a native crash
> ends only the child. That choice belongs to M5.1b-2 and awaits approval. Pause and the
> never-terminate-mid-batch rule apply to both.

- **Pause:**
  1. set the cancel flag; the worker stops before its next batch;
  2. put the claimed row back to `pending` (token cleared) in a short transaction;
     nothing partial is ever written;
  3. `Embedder.close()`: drain, release, natural exit;
  4. release the indexer lock.
- **Why the drain is mandatory:** the spike measured that ending a worker thread while
  ONNX Runtime is inferring **aborts the whole process**:
  - `process.exit()` and `worker.terminate()` mid-batch: SIGABRT, 8 of 8 each;
  - the same while the worker is idle: clean;
  - the cooperative drain: clean, 27–189 ms.
- **Next.js exits too early by itself:** without help, Next.js calls `process.exit()`
  milliseconds after SIGINT/SIGTERM. `next dev` also SIGKILLs its server 100 ms later.
- **Signal handling, so ThreadAtlas owns the exit:**
  - `"start": "NEXT_MANUAL_SIG_HANDLE=true NEXT_TELEMETRY_DISABLED=1 next start --hostname 127.0.0.1"`;
  - `"dev": "NEXT_MANUAL_SIG_HANDLE=true NEXT_EXIT_TIMEOUT_MS=15000 NEXT_TELEMETRY_DISABLED=1 next dev --hostname 127.0.0.1"`;
  - `src/instrumentation.ts` `register()` (Node.js runtime only) installs one SIGINT and
    SIGTERM handler, guarded by a `globalThis` flag. Because Next no longer exits by
    itself, the handler **always** exits the process with 130 or 143, even if the indexer
    never ran.
- **On a signal:**
  1. pause the indexer as above (if running);
  2. wait for the write lock to be free, up to the 10 s target, so an in-flight import or
     delete-all reaches a transaction boundary (Next's own handler used to let open
     requests finish); both are already crash-safe (M1.4, M1.7), so stopping later is
     safe;
  3. exit.
- **The 10 s target is never a reason to terminate a worker that is inferring.** If it
  passes mid-batch (not observed; a batch takes ≤ 0.3 s), the handler keeps waiting for
  the batch to finish and the session to be released. A SIGKILL from outside (or the
  `next dev` parent after 15 s) remains the only hard stop. It is an operating-system
  kill, which the spike showed causes no abort, and recovery is I5.
- **Measured with this setup:**
  - `next start`: drained in 44–117 ms, 6 of 6;
  - `next dev`: 60–189 ms, 5 of 5;
  - Next's default handling: SIGABRT 3 of 3 (`next start`) and 1 of 1 (`next dev`).
- **Platform caveats:**
  - Next documents `NEXT_MANUAL_SIG_HANDLE` for `next start` (on a Pages Router page) and
    says it is unavailable in `next dev`; it works in 16.4.4.
  - `NEXT_EXIT_TIMEOUT_MS` is undocumented.
  - A test pins both scripts, and the drain is re-checked after every Next.js upgrade.
    If either stops working, the consequence is a crash at shutdown, never data loss.
- **Accepted dev-only limitation:** a `next.config.ts` change during a batch makes
  `next dev` restart through `process.exit()`, which aborts and ends the dev session
  (measured). Documented; recovered by I5 at the next Start.

### 5.8 Live and stale `running` rows (correction D)

After a crash or SIGKILL, rows stay `running` until the next Start (I5). The status must
not present them as indexing in progress.

- **Liveness is decided by the process, never by the row:**
  - **This process:** the indexer singleton on `globalThis` (§8) knows whether it is
    running, pausing or waiting.
  - **Another process:** a non-blocking probe of the indexer lock, the existing
    `tryAcquireWriteLock` mechanism on `<db>.index-lock` with no retries. A probe that
    gets the lock releases it at once. A Start that races with a probe retries (≈ 150 ms,
    as today), so a probe never makes a Start fail.
- **Status:**

  | `running` rows | This process indexing | Lock held elsewhere | Shown as |
  | --- | --- | --- | --- |
  | any | yes | — | **indexing** (live) |
  | any | no | yes | **indexing in another ThreadAtlas process** |
  | > 0 | no | no | **interrupted**: "N conversations will be indexed again at the next Start"; counted as waiting |
  | 0 | no | no | idle (up to date / N waiting / failures) |

- **The status never writes.** The reset happens only at Start, under the indexer lock (I5).

### 5.9 Crash recovery

| Crash point | State left | Recovery |
| --- | --- | --- |
| Before or inside T1 | T1 rolled back | none needed |
| During inference (pages, windows) | row `running` with a dead token; shown as *interrupted* (§5.8) | reset at next Start (I5); re-embedded; the attempt counts (§5.6) |
| Inside T2 | T2 rolled back; row still `running` | as above |
| After T2 | committed | none |

SQLite's rollback journal (DELETE mode, as today) guarantees T1 and T2 are atomic. The
OS releases both locks on SIGKILL (measured in M1.4: about 4 ms).

### 5.10 Model or chunker change

The configuration check in Reconcile compares every field (§5.2 step 3). Old vectors are
unreadable from the moment the code changes, before Reconcile runs (I7).

## 6. Locks and transaction boundaries (approved, decision 2)

| Lock | Holder | Duration | Purpose |
| --- | --- | --- | --- |
| Write lock (`<db>.lock`, existing) | import, delete-all, indexer T1/T2/reconcile/pause-reset | whole import or delete-all; milliseconds for the indexer (T2 at the chunk cap: measured, target < 500 ms) | serialises all writes across processes |
| **Indexer lock** (`<db>.index-lock`, new, same mechanism as `write-lock.ts`) | the indexing session | from Start until Pause, finish or shutdown | at most one indexer per database across processes; makes the I5 reset safe; probed for liveness (§5.8) |

- **Lock order:** indexer lock, then write lock; never the reverse. Import and delete-all
  never take the indexer lock: they invalidate through I2 and I3 and never wait for the
  indexer.
- **Connection:** all writes go through the existing single writer connection
  (`runWriterTransaction`). Inference and page reads never hold a transaction.

## 7. The vector-read function (correction B)

M5.2's search will read vectors only through one function, `openVectorReader()`.
M5.1b implements and tests it, but nothing in the app calls it yet.

1. **Configuration (I7):** read the `EmbeddingIndex` row.
   - If there is no row: `INDEX_EMPTY`.
   - If any of `embeddingVersion`, `chunkerVersion`, `chunkTokens`, `quantization` or
     `dimensions` differs from the code's constants: `INDEX_INCOMPATIBLE`.
   - In either case it returns no vectors. The caller (M5.2) falls back to keyword
     search with a static message, "the semantic index needs rebuilding".
2. **The query side:** the querying Embedder's reported `embeddingVersion` and
   `chunkerVersion` must equal the stored row's; otherwise `INDEX_INCOMPATIBLE`.
3. **Rows (I6):** chunks are joined to `Conversation` on id and version, with
   `chunk.epoch = EmbeddingIndex.epoch`.
4. **Bytes:** a vector whose length is not `quantizedByteLength(dimensions)` is never
   decoded. It is skipped and counted, and the count is shown in Settings as an integrity
   warning.
5. **One snapshot:** the configuration and the rows are read in one read transaction, so
   a concurrent Reconcile can't mix configurations.

This is what makes a stored index from another model, chunker, budget, quantisation or
dimension count unreadable immediately after a code change, even if the user never
presses Start.

## 8. Server integration (decision 6, spike results)

> **2026-11-11:** loading from source is approved (D124). The host for native
> inference, a worker thread or a child process, is decided in M5.1b-2. The comparison
> recommends the child process (see §5.7).

- **Worker loading: from source.** The spike found both approaches work in `next dev`
  and `next start`, with vectors bit-identical to plain Node and a 1.0–1.3 s start.
  - Source loading is chosen because it is the tested path: Node loads
    `src/lib/semantic/worker.ts` itself, and ONNX Runtime and the tokenizer come from
    `node_modules`, exactly as in the M5.1a tests.
  - It does not depend on Turbopack's newer worker-thread bundling.
  - Bundling remains a measured fallback.
- **Required change to `embedder.ts`:**
  - The committed `new Worker(opts.workerUrl ?? new URL("./worker.ts", import.meta.url))`
    can't be analysed by Turbopack. In the spike it made every JS, TS and JSON file in
    the project a worker entry (928 chunks) and broke the route's compilation.
  - The constructor becomes `new Worker(/* turbopackIgnore: true */ workerUrl, …)`, with
    no `import.meta.url` fallback.
  - `workerUrl` comes from one helper, `sourceWorkerUrl(projectRoot)`. It requires
    `<root>/src/lib/semantic/package.json` and `worker.ts` to exist, so a wrong working
    directory gives `RUNTIME_UNAVAILABLE` instead of a confusing failure.
  - Tests keep passing their own entries.
- **The singleton lives only on `globalThis`** (`globalThis.__threadatlasIndexer`): the
  indexer, its Embedder, the run state and the signal-handler flag. The spike found:
  - `instrumentation.ts` and route modules get separate module instances;
  - every HMR edit re-evaluates the module;
  - a module-scoped Embedder leaked one live worker per edit, while the `globalThis` one
    was reused.
- **Signals:** see §5.7.
- **Build output:** Next's file tracer includes `src/lib/semantic/*` in the route traces.
  It is harmless without standalone output, so it is left as is.

## 9. Delete-all, secure deletion and cleanup

- **Phase 1 (logical deletion):** the existing transaction (with `secure_delete = ON`)
  also:
  - deletes all `EmbeddingChunk` and `EmbeddingStatus` rows, explicitly (the cascade is a
    second line of defence);
  - increments `EmbeddingIndex.epoch` and `changeCounter`.

  The `EmbeddingIndex` row is kept: it holds only versions and counters, no imported
  data (decision 4).
- **Phase 2 (cleanup):**
  - the existing `VACUUM` with `temp_store = MEMORY` covers the new tables;
  - verification adds: both tables empty, `quick_check` ok, no free pages;
  - standalone cleanup (`finishStorageCleanup`) also refuses to run while chunks exist.
- **During an indexing run:**
  - an in-flight commit fails I4 (epoch and conversation both gone);
  - the run continues, finds no rows, and stops;
  - the status shows the empty index.
- **Replacement and remanence:** on replace, old vectors are deleted without
  `secure_delete`, exactly like replaced message text today. Their bytes can persist in
  free pages until delete-all's VACUUM. Documented as a limitation, as for message text.
- **Measured basis (Experiment 2):** after deletion, secure delete and VACUUM, no deleted
  vector bytes remained in the file.

## 10. Backup and migration safety

1. **Review:** the final migration SQL is reviewed, and its SHA-256 recorded, before any
   use.
2. **Rehearsal** on synthetic databases in a guarded temporary directory, as for M2.1:
   - deploy onto a populated synthetic M2 database;
   - verify (integrity check, FTS5 checks, row fingerprints unchanged, new tables empty,
     `migrate status`, `db:check-migrations`);
   - restore from backup, redeploy;
   - a deliberately failing migration;
   - path guards;
   - no outbound connection.
3. **Real database:** only with separate approval at that time.
   - **Before:** stop the dev server; check that no process holds the database or its
     lock; make a fresh backup with SQLite's backup API into `data/backups/` (0700/0600)
     with a manifest, verified (integrity, row fingerprint, migration history).
   - **Apply:** `npm run db:deploy`.
   - **After:** verify as in the rehearsal.

   The existing M2.1 backup is not touched; removing it remains the user's decision.
   - **Ordering:** once the import code writes status rows (I2), the app needs the new
     tables. The commit that adds I2 and the real-database migration go together, as for
     M2.1.
4. **Rollback:** the migration is purely additive and the tables hold only derived data,
   so `DROP TABLE` of the three tables returns the M2 schema with no loss. A backup
   restore remains the primary path.
5. **No other data migration:** nothing is backfilled by the migration; Reconcile queues
   existing conversations at the first Start.

## 11. Settings: status, progress and errors

A "Semantic index" section with:
- **Status:**
  - model: installed and verified, missing, or invalid;
  - conversations indexed out of total; waiting, failed (with "too large" counted
    separately);
  - chunks;
  - the current run's progress (conversations done out of queued, chunks per second, an
    estimate);
  - the last error, as a static message;
  - an integrity warning if the reader skipped malformed vectors (§7).
- **Start / Resume:** a guarded Server Action with the same Origin, Host and
  `Next-Action` checks as delete-all; idempotent while running.
- **Pause:** cooperative; the button shows "Pausing…" until the in-flight batch has
  finished.
- **Retry failed:** resets `failed` rows to `pending` (attempts 0). Too-large
  conversations fail again; the message says so.
- **Polling:** every 2 s while the page is open (decision 5), through a no-store route or
  Server Action that returns counts and states only (no text, ids or vectors).
- **States:**
  - model missing (with the `npm run model:fetch` instruction);
  - runtime unavailable;
  - idle (never indexed / up to date / N waiting);
  - running;
  - waiting for import (write lock busy);
  - pausing, paused;
  - **interrupted** (stale `running` rows, §5.8);
  - indexing in another process;
  - index incompatible: "will be rebuilt at the next Start" (§7);
  - finished with failures;
  - failed (run-level code).

Every message is static; no text, path or native error appears.

## 12. Tests (M5.1b)

A deterministic fake embedder (hash-based vectors, controllable delays and failures)
runs through the real worker loop; the real model is used only in opt-in tests.

**Stale vectors cannot reappear (the core requirement):**
1. **Replacement during inference** (`beforeCommit` hook):
   - the commit is discarded;
   - only the new version's chunks exist after the next run;
   - their offsets fit the new text.
2. **Reprocessed during inference** (same `contentHash`, newer parser): the commit is
   discarded. This is the case the proposal's design missed.
3. **Delete-all during inference:** no chunks or status rows afterwards; re-importing the
   same export during the old run never shows the old vectors.
4. **A→B→A replacement during one inference:** the commit is discarded by the token and
   re-embedded. This is safe by design, not by content comparison.
5. **Replacement between two pages** (correction C): stopped at the next page, nothing
   written, no attempt counted.
6. **Configuration change:** all chunks dropped, epoch incremented, everything queued.
   A hand-inserted stale row (old epoch, or old version) is never returned by the reader
   (I6).
7. **Incompatible stored configuration before Reconcile** (correction B): with each of
   the five fields changed in turn, the reader returns `INDEX_INCOMPATIBLE` and no
   vectors, while the rows' epoch still matches. A query embedder reporting another
   version is refused. A malformed vector length is skipped and counted.
8. **Replace without indexing:** the old chunks are gone in the same transaction as the
   old messages. Checked by rolling the import back with a fault hook: chunks and
   messages are both unchanged.

**Lifecycle:**
- **Zero eligible messages** (correction A): such a conversation (only hidden or
  structural messages, or only whitespace) becomes `indexed` with `chunkCount = 0`. Three
  further Starts queue nothing.
- **A conversation at the chunk cap** (correction C): indexed in one T2. Peak heap growth
  and T2 duration are measured against the budget. Cap + 1 fails with
  `CONVERSATION_TOO_LARGE` with no retries.
- **Window determinism:** a conversation spanning several windows and pages has
  bit-identical vectors on reindex and in a fresh process.
- **Stale `running` rows** (correction D): after SIGKILL of a child indexer the status
  shows *interrupted*, not *indexing*. A second live process shows *indexing in another
  process*. The probe never makes a concurrent Start fail (repeated race test).
- **Failure classes** (§5.6):
  - a poison conversation (recoverable error): `failed` after 3 attempts, the others are
    indexed;
  - a model or runtime failure stops the run with the attempt refunded;
  - a worker crash keeps the attempt.
- cancel and resume with exactly the full chunk set;
- pause during a batch: the batch finishes, the row is `pending`, nothing partial is
  written;
- SIGKILL of a child indexer at every crash point in §5.9, then recovery: no duplicates,
  the chunk set equals a full rebuild, `integrity_check` ok;
- a second process refused by the indexer lock;
- write-lock contention: the indexer waits and never blocks an import;
- backfill of conversations imported before the migration;
- event-loop responsiveness during a run.

**Server integration:**
- **The scripts:** a test pins `NEXT_MANUAL_SIG_HANDLE=true` in `dev` and `start` and
  `NEXT_EXIT_TIMEOUT_MS` in `dev`.
- **The handler:** installed once (the `globalThis` guard); always exits; never calls
  `terminate()` while a request is in flight; waits for the write lock up to the target.
- **Built-server drain:** a production server with the fake embedder in a busy batch
  gets SIGTERM; the exit code is 143, there is no abort output, and the row is `pending`.
- `sourceWorkerUrl` refuses a wrong root.

**Delete-all:**
- canary vectors (a distinctive 388-byte pattern) absent from the database file after
  delete-all;
- both tables empty, no free pages, `quick_check` ok;
- standalone cleanup refuses while chunks exist.

**Schema and migration:**
- `db:check-migrations` and the drift test with the new models;
- a schema test for the tables, indexes and foreign keys (cascade);
- the migration rehearsal script.

**UI (e2e, fake embedder):**
- Settings status for each state, including *interrupted* and *incompatible*;
- Start, progress, Pause, Resume, Retry failed;
- guard checks on the actions;
- no text or ids in the polling response.

**Opt-in real model:** a full index of the synthetic research sets, chunk count and
quality equal to the M5.1a model tests (re-run with the window rule).

## 13. Decisions

**Approved 2026-11-10 (D123), with the owner's conditions:**
1. The generation: `contentHash` + `parserVersion` + claim token + epoch.
2. The second indexer lock and the documented lock order.
3. Three attempts and a persistent `failed` state. Recoverable per-conversation errors are
   retried; model, runtime and configuration failures stop the run (§5.6).
4. `EmbeddingIndex` metadata kept after delete-all.
5. 2 s polling and a 10 s graceful-shutdown target. An active inference worker is never
   force-terminated to meet the deadline (§5.7).
6. Both worker-loading approaches tested before selecting one. Tested; source loading
   recommended (§8).
- The three-table schema direction, with int8 vectors and character offsets, without
  duplicate message text.

**Decided 2026-11-11 (D124):**
1. **Approved:** `EmbeddingJob` renamed to `EmbeddingStatus`; successful rows kept,
   including zero-chunk completions.
2. **Approved:** the worker loaded from source through the explicit path that keeps
   Next.js from bundling the project.
3. **Conditional:** the `NEXT_MANUAL_SIG_HANDLE` / `NEXT_EXIT_TIMEOUT_MS` workaround may

   Compared with a child process (recommended; awaiting approval).
4. **Approved:** bounded paging, groups of 256 chunks and the initial 20,000-chunk cap
   as an **internal constant**. Oversized conversations fail gracefully, without
   affecting other jobs or keyword search.
5. **Approved:** claim-based attempt counting with refunds for clean run-level failures.
6. **Accepted for now:** the dev-only `next.config.ts` limitation (it disappears with
   the child process).

  gate; M5.1b-2 (server integration and Settings) subject to a separate approval.

**Points as they were presented for approval on 2026-11-10 (kept for the record):**
1. **Rename `EmbeddingJob` to `EmbeddingStatus`** and keep the row after success (state
   `indexed`, new column `chunkCount`) (correction A). Still three tables.
2. **Source-loaded worker** with the `embedder.ts` change in §8.
3. **Own the shutdown signals:** `NEXT_MANUAL_SIG_HANDLE=true` in `dev` and `start`,
   `NEXT_EXIT_TIMEOUT_MS=15000` in `dev`, and the handler in `src/instrumentation.ts`.
   This relies on one documented-for-production and one undocumented Next.js behaviour,
   pinned by tests.
4. **The memory bounds:** pages of 200 messages / 1,000,000 code units, windows of 256
   chunks (added to `EMBEDDING_VERSION`), a cap of 20,000 chunks per conversation, and
   `CONVERSATION_TOO_LARGE` as a permanent failure rather than partial indexing.
5. **The attempt accounting** in §5.6: count at claim, refund on a clean run-level
   failure, keep on a worker crash.
6. **Accept the dev-only limitation:** a `next.config.ts` change during a batch crashes
   `next dev`.

## M5.1b-1 implementation notes (2026-11-11, for review)

Implemented in `src/lib/semantic/index/` as planned. Differences from this design and the
plan, each tested:

1. **Chunk inserts (T2).** Planned: positional parameters, at most 500 rows per
   statement (11 parameters per row). Measured at the 20,000-chunk cap: 420–490 ms of
   write-lock hold, mostly Prisma's per-parameter handling (better-sqlite3 directly:
   106 ms). Now each statement passes two parameters: the rows' offsets and keys as one
   JSON array, and their vectors as one concatenated blob, which SQLite cuts at the fixed
   388-byte stride (`json_each`, `substr`). Up to 1,000 rows per statement, with a yield
   between statements. Still one transaction (all chunks or none), on the same writer
   connection; the vector stride and the inserted row count are checked. Measured:
   164 ms at the cap. A round-trip test checks every byte and unusual node ids.
2. **Indexer-lock retries.** Planned: the write lock's short retries (6 attempts, about
   150 ms). The repeated race test found that liveness probes from another process every
   1–3 ms made one Start fail. The indexer lock now has 20 attempts (about 0.5 s); the
   same test passed 4 of 4 times. Status polling is planned every 2 s, far less often.
3. **Page budget in characters.** The 1,000,000 budget per page is counted with SQLite's
   `length()`, which counts code points, because T1 reads no text. A page of
   supplementary-plane text can therefore hold up to 2,000,000 UTF-16 code units (about
   4 MB). The worker's 1,000,000-unit input limit is checked exactly when the text is
   read (`CONVERSATION_TOO_LARGE`).
4. **Page reads use a reader connection,** never the writer: an import in the same process
   may hold a transaction open on the writer, and its uncommitted rows must not be read.
   `runIndexer` therefore takes `{ writer, reader, … }`.
5. **The singleton (owner's condition C).** Every statement addresses the row by
   `INDEX_ROW_ID`. A row with another id (possible only by editing the file) makes the
   reader return `INDEX_INCOMPATIBLE` and the status show *incompatible*; the next
   Reconcile deletes it and rebuilds the index (`rebuilt: "singleton-repaired"`). A
   missing row is recreated above every stored epoch.
6. **Codes.** Besides the five planned codes: `INDEXER_LOCK_FAILED` (the indexer lock
   could not be taken safely) and `WRITE_LOCK_FAILED` (run-level).
7. **Retry failed** keeps `lastErrorCode`, so a too-large conversation is still shown as
   such until it fails again.
8. **Status states** (`status.ts`): `indexing`, `waiting-for-import`, `pausing`,
   `indexing-elsewhere`, `interrupted`, `incompatible`, `never-indexed`, `run-failed`,
   `waiting`, `finished-with-failures`, `up-to-date`. Model availability states (§11)
   belong to M5.1b-2.
9. **Pause while an import holds the write lock:** the claimed row's refund waits for the
   lock (an import holds it only for its own duration), so a pause never loses an
   attempt.

### Final verification changes (2026-11-11, owner's audit)

10. **Imports and delete-all wait up to 1 s for the write lock** (`IMPORT_LOCK_WAIT_MS`;
    before: 6 attempts, about 50–200 ms). Measured across processes: with the old retries
    an import starting during a hold of 250 ms failed 3 of 4 times, of 500 ms or more 4 of
    4; with the wait it succeeded for holds up to 900 ms and was refused after 1.00–1.02 s
    for a 1,500 ms hold. In the same process an import during a T2 at the cap succeeded
    8 of 8 before and after (T2's statements also delay the import's retry timers). The
    indexer keeps the short retries (its own loop waits and yields to imports).
11. **Chunk rows are validated before T2 writes anything** (`validChunkRows`): at most
    20,000 rows (the cap is also enforced at the commit), non-empty ids, non-negative safe
    integers with `start < end`, vectors of exactly 388 bytes, unique keys. The indexer
    also checks that every chunk the worker returns is an exact substring of the page it
    just read; a reply that is not is a recoverable `INFERENCE_FAILED`.
12. **Two independent stale-read layers, each tested on its own:** the page read's token
    check stops a changed claim at the next page (no inference on stale text), and T2's
    compare-and-set refuses it regardless (removing the page check in a test still left
    nothing stale committed).
13. **Test isolation guard** (`src/lib/db/path.ts`): the real path is compared as a string
    before any filesystem call; only the candidate is inspected (symlinks and multiply
    linked files refused without being followed). Tests that used to stat the real
    database's metadata, or point the Prisma CLI at its path to prove the refusal, now use
    a decoy project root.
